DriveTest Analyzer · CDR compatibility report

Compatibility of Umlaut CDRs with DriveTest Analyzer

A comparison of the NetCheck CDRs the tool is built for with the Umlaut export of WindTre (Vendor Benchmark 2025, Round 1): which fields each module uses, what each would have with Umlaut, and how to adapt the tool without losing features.

Version 4 · 24 October 2026Branch 0.8.7NetCheck reference: UK Q3 2026 SA and NSA CDRs

Today there is no compatibility: the Umlaut CDR type is disabled and, if the files are uploaded to a NetCheck workspace, the type is detected wrongly, the Statistics sheet comes in as data and the modules do not find their columns.

Adapting it is feasible. Of the 109 groups of NetCheck fields the tool uses, 84 (77%) have in Umlaut the same data, the same data with another unit or values, or an exact calculation; 17 can be approximated and 8 are missing.

Chosen model: one provider per workspace (NetCheck, Umlaut and later P3), with each provider’s names and values visible to its users. A profile per provider tells every module where each piece of data is, and Scoring, PPT and NQ use each provider’s own content. Network Insights is the module that changes most, because of the radio and cells of the calls. The first phase, the multi-provider base with no change for NetCheck, is done in version 0.8.7.

  • DirectThe same data under another name: renaming the column is enough.
  • ConversionThe same data with another unit or other values: rename and convert (kbit/s→Mbit/s, SUCCESS→Completed…).
  • DerivableNot a column, but calculated exactly from other Umlaut fields.
  • ApproximateAn approximation is possible with another definition or less detail (a snapshot instead of an average, a text instead of a hierarchy…).
  • MissingUmlaut does not bring this data; the feature that uses it shows empty or uses another metric.

Compatibility per module

Which fields each module reads and what it needs to work with Umlaut, from most direct to most complex.

Workspace and CDR ingestion

Major changes

Fields it uses: Fixed columns: Operator, Campaign, Region, Zone (G_Level_3), City (G_Level_4), Session_Type/Type_of_Test, Test_Name, Call_Status/Test_Result, start and end times, RAT/RAT_A, Vendor. It also derives setup_time, duration, quality, throughput, latency, jitter, handovers and technology_primary.

  • The Umlaut CDR type is disabled in Workspace Config ("supported": False in cdr_types.py).
  • NetCheck delivers one workbook per type with one sheet per operator after "KPI Definition"; Umlaut delivers one file per service (9 for data, 2 for calls, 2 for samples) with a "Statistics" sheet that today would be imported as data.
  • Type detection by name fails: "Voice_M2M_SQ_Samples" would be taken as Voice (it is Speech) and "HTTP_File_DL", "Ping", "Youtube" or "Conversational_App_*" are not recognised.
  • Headers repeated per side (Sequence, Filename, Route Name… appear twice), names with spaces and brackets, different units and status vocabulary, no Campaign and no JOIN_ID.

Multi-provider proposal

The tool will work with NetCheck, Umlaut and later P3 CDRs, each in its own workspaces and with its own vocabulary. This proposal replaces the one in the first version of the report, which translated Umlaut into NetCheck names.

Decisions

  • One provider per workspace. A workspace is created as NetCheck, Umlaut or P3 (the CDR type setting that already exists) and the provider does not change once it has CDRs. The CDRs of several providers are never mixed.
  • Native names. Every CDR is stored with its original columns and users see the names, values and files of their provider. Umlaut is not translated into NetCheck names.
  • Umlaut Scoring. The NetCheck methodology is not adapted: the Umlaut one will be implemented when it is available, written with the Umlaut fields.
  • NQ in Umlaut. The calls, tests and samples with Qualifier = NOT QUALIFIED in their own column.
  • RCA. When the provider brings an RCA it is one more source. The DT Analyzer RCA is the common engine in every workspace, after the Ericsson RCA, which is adapted to the call key of each provider.

Three layers per provider

Provider readerCode per providerUnderstands the structure of the export: which files and sheets are CDRs, the type of each (Data, Voice, Speech), sheets to ignore (KPI Definition in NetCheck, Statistics in Umlaut), headers repeated per side and joins (each SQ sample with its call).
Provider profileDeclarative configurationTells the fixed part of every module where each concept is (result, start, coordinates, cell, RSRP, setup, MOS, call key, whether the call is NQ…), with the native column, the conversion and the meaning of the values. Detects campaign, operator, NR Mode and stage.
Provider contentAssets and Workspace ConfigScoring methodologies, PPT templates, auto-calculated fields, queries, RCA catalogue and Campaign Maps written with the provider’s names and values.
ModulesCommon logicScoring, PPT, NQ, Network Insights, CDR Analysis, Builders and Reporting read the data through the profile and use the content of the workspace’s provider.

The tool already has an internal layer of its own names (status, success, setup_time_seconds, throughput_mbps, technology_primary…) and alias tables in NQ (FIELD_SOURCES) and Network Insights (RF_FIELD_ALIASES), written today for NetCheck. The provider profile is what fills them. Whatever the provider does not bring and the tool needs (call key, ECI, mean radio of the call) is added as derived columns, marked as such.

RCA

  • Today the "NetCheck RCA" section of NQ suggests a domain and a cause with keywords on Failure_Classification, Category, Subcategory and Comment. That rule engine is already generic: what is NetCheck-specific are the fields and the catalogue.
  • Available in every workspace since version 0.8.7, with rules that can be edited: the DT Analyzer RCA uses the failure fields of each provider’s profile and adds conditions on the failing phase and the radio at the time of the failure (for example RSRP < −110 dBm → coverage, SINR < 0 dB → interference, a failure in DNS or service access → core or server).
  • For Umlaut it can read Failure Indication, Sequence Detailed Status Overall, the status of each phase (network access, DNS, connection, service access, TTFB, transfer) and the radio at the start and the end.
  • The NetCheck RCA is one more source in NetCheck workspaces, like the Ericsson one. The Ericsson RCA, imported today by JOIN_ID, would be imported by the provider’s call key.

Project requirements that apply

  • The field dictionary of each provider is transferable configuration: it goes into Import/Export, Transfers, Backup and Restore, with round-trip compatibility.
  • If it is stored in a new table, it must appear in Database Management with a title in the "CDR Field Dictionary" format.
  • Every upload, mapping change and reprocessing is recorded in App Events with enough detail to troubleshoot errors.
  • Code, labels and messages in English; Help updated (Workspace, Scoring, NQ, Network Insights) and the changelog of the current version.
  • Changing the NQ index requires raising its schema version so existing workspaces are reindexed.

Limits of 100%

With the Umlaut profile every feature of the tool works with Umlaut, but some data cannot be obtained from these exports. In those cases the panel or slide shows "not available in Umlaut CDRs" or uses the closest Umlaut metric.

  • No equivalent: TikTok test (K33–K35), FDTT UL over UDP, SIP/CC signalling timestamps, RTP jitter and loss, POLQA internal parameters, NR RBs and UL MCS, RAT_Timeline and the list of handovers.
  • A different definition: Disturbed & Impaired (Call Sustainability), Irritating Video (interruptions), Browsing Success (1000 KB), Call Setup Time (Alerting or Option D), Receive Delay (mouth to ear).
  • Less detail: radio of the calls (start and end, or the mean of the samples), cells (only start and end; NR without NCI), RCA (a text instead of the NetCheck hierarchy).
  • In exchange Umlaut brings the Qualifier, the status and duration of every phase of the tests, throughput per chunk, CA detail per carrier, two setup definitions, mouth-to-ear latency and quality per side, which can be added as new metrics.
